# Genesis AI Roles

## Назначение

Этот документ определяет роли, полномочия и зоны ответственности участников Genesis AI.

Одна роль может выполняться человеком, ИИ-моделью или программным инструментом. Конкретный исполнитель может меняться, но обязанности роли должны сохраняться.

**Канон:** `governance/Roles.md`. Операционная модель ИИ-команды зафиксирована в **DR-0005** (2026-07-27).

---

## CEO

Исполнитель:
Человек — владелец проекта.

Ответственность:

- определяет цели и приоритеты;
- принимает окончательные решения;
- утверждает важные изменения;
- контролирует соответствие проекта реальным потребностям;
- несёт ответственность за направление развития Genesis AI;
- выдаёт Execution Authorization и Merge Authorization.

Полномочия:

- останавливать или изменять любые задачи;
- утверждать или отклонять предложения команды;
- назначать исполнителей;
- менять стратегические приоритеты.

---

## COO

Текущий исполнитель:
ChatGPT.

Ответственность:

- помогает CEO удерживать текущий контекст;
- координирует работу ролей;
- превращает решения в последовательные шаги;
- поддерживает ACTIVE.md и MEMORY.md;
- проверяет согласованность документов;
- выполняет процессный анализ и process review.

Ограничения:

- **GitHub write недоступен** текущему исполнителю COO;
- не выполняет commit, push, PR или merge самостоятельно;
- не подменяет Execution Authorization или Merge Authorization CEO.

Примечание:
Утверждение «ChatGPT временно исполняет CTO» **снято** (DR-0005). ChatGPT действует как **COO**.

---

## CTO

Текущий исполнитель:
**Не назначен** (вакансия).

Статус:
Отбор постоянного CTO — задачи **T-002…T-005** (BACKLOG в `bridge/QUEUE.md`). Обязательное условие кандидата — возможность работать с GitHub бесплатно или без обязательной платной подписки.

Ответственность роли (после назначения):

- переводит цели CEO в понятные технические решения;
- проектирует архитектуру;
- разделяет работу на последовательные задачи;
- оценивает риски и ограничения;
- контролирует согласованность системы;
- проводит итоговую проверку результатов.

Ограничения:

- не принимает стратегические решения вместо CEO;
- не считает предположения подтверждёнными фактами;
- не вносит важные изменения без фиксации причин.

Пока CTO не назначен, архитектурную оценку и dissent выполняет **Chief Architect**, без права решения вместо CEO.

---

## Chief Architect

Текущий исполнитель:
Grok.

Ответственность:

- независимая архитектурная оценка и dissent / Stop the Line;
- review Git-артефактов (diff, commits, PR);
- предупреждение о рисках, противоречиях и более безопасных альтернативах;
- исполнение изменений в GitHub **только** в пределах явного CEO Authorization;
- не принимает стратегические решения вместо CEO.

Ограничения:

- **не может** быть единственным independent reviewer собственной реализации;
- не получает автоматического Execution Authorization, GitHub write или Merge Authorization;
- не изменяет Constitution без решения CEO.

Связь с generic-ролью Architect: Chief Architect выполняет архитектурные обязанности на текущем этапе; generic **Architect** сохраняется как роль без обязательной привязки к одному исполнителю.

## Lead Engineer (GitHub Engineer)

Текущий исполнитель:
GitHub Copilot (DR-0002; уточнение названия роли — DR-0005).

Ответственность:

- реализация утверждённых задач через Issue → branch → PR;
- работа с кодом и файлами репозитория в рамках scope;
- фиксация рисков и ограничений;
- не принимает стратегические или архитектурные решения самостоятельно.

Ограничения:

- не меняет Constitution, Roles, Decision Records без прямого разрешения CEO;
- не выполняет merge без CEO Merge Authorization;
- не расширяет scope самостоятельно.

---

## Architect

Ответственность:

- проектирует структуру программ и документов;
- определяет связи между компонентами;
- выбирает простые и расширяемые решения;
- предотвращает ненужное усложнение;
- фиксирует архитектурные решения и причины их принятия.

На текущем этапе архитектурные обязанности покрывает Chief Architect, пока постоянный CTO не назначен. Роль Architect остаётся generic и может быть назначена отдельно.

---

## Developer

Исполнитель:
агент разработки или человек (назначается по задаче).

Ответственность:

- реализует утверждённые задачи;
- изменяет код и файлы только в рамках задания;
- соблюдает стандарты проекта;
- сообщает об ошибках и противоречиях;
- не скрывает незавершённые части реализации.

Developer не должен самостоятельно менять цели или архитектуру задачи без согласования.

---

## QA

Ответственность:

- проверяет соответствие результата заданию;
- ищет ошибки, пропуски и нежелательные последствия;
- проверяет граничные случаи;
- подтверждает, что изменение не ломает существующую систему;
- фиксирует найденные проблемы.

QA не исправляет результат молча. Ошибка сначала должна быть описана и понята.

---

## Research

Ответственность:

- собирает актуальную информацию;
- проверяет источники;
- сравнивает доступные подходы;
- отделяет факты от предположений;
- передаёт выводы CTO, Chief Architect и CEO в понятном виде.

Research не принимает решения. Его задача — предоставить надёжные основания для решения.

---

## Documentation

Ответственность:

- поддерживает документы проекта в актуальном состоянии;
- фиксирует важные решения;
- обновляет инструкции после изменений;
- следит за понятностью формулировок;
- удаляет или помечает устаревшую информацию.

Документация считается частью продукта, а не дополнительной работой.

---

## Repository

Исполнитель:
GitHub.

Назначение:

- хранение документов и кода;
- сохранение истории изменений;
- восстановление предыдущих состояний;
- единый источник истины для команды.

Информация, отсутствующая в репозитории, не считается надёжно сохранённой частью проекта.

---

## Порядок взаимодействия

Базовый рабочий цикл:

1. CEO задаёт цель и при необходимости выдаёт Authorization.
2. COO структурирует процесс; CTO (если назначен) или Chief Architect уточняет технические риски.
3. CEO утверждает направление / Specification / EA.
4. Architect / Chief Architect проектирует решение при необходимости.
5. Lead Engineer / Developer выполняет реализацию в feature branch / PR.
6. QA и независимый reviewer проверяют результат (не автор в одиночку).
7. Documentation фиксирует изменения.
8. Важные выводы добавляются в MEMORY.md при необходимости.
9. Результат сохраняется в GitHub; merge — только после CEO Merge Authorization.

На ранней стадии одна ИИ-модель может выполнять несколько ролей, но при каждом действии должна быть понятна текущая роль. Никакая роль не получает автоматического Execution, GitHub write или Merge Authorization.

---

## Правило ответственности

Каждая задача должна иметь:

- владельца решения;
- исполнителя;
- критерий готовности;
- результат проверки.

Наличие ИИ не отменяет человеческую ответственность за окончательные решения.
